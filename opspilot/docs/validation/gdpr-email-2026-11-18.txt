## Brevo transport

Unit-tested through an injected `fetch`, so the logic is exercised without a network:

- 201 + `{messageId}` -> `{status:"sent", providerId}`; request body asserted
  (`sender` parsed from `OpsPilot <addr>`, `to` array, `textContent`, `subject`) and the
  `api-key` header.
- 401 -> failure containing "Check BREVO_API_KEY."
- 400 (unverified sender) -> "Verify the MAIL_FROM address … (no domain required)".
- 402 -> "Daily free-plan quota exhausted (300/day)"; 429 -> rate-limit hint; 418 -> no hint.
- network error -> `{status:"failed"}` with the message; a 2xx with an unparseable body is
  still treated as delivered.
- config: missing key or invalid MAIL_FROM throws `ConfigError` at boot.

**Not verified:** a real Brevo delivery. No account exists and this sandbox cannot reach
api.brevo.com, so `MAIL_TRANSPORT` stays `console` here and nothing was sent.

## GDPR endpoints

```
GET /api/account/export  (anonymous)              -> 401
GET /api/account/export  (owner)                  -> 200, attachment; filename="opspilot-export-2026-11-18.json"
   payload keys: account, workspace(+members), records, payments, stockMovements,
   documents(metadata only), notifications, auditEvents, subscription, emailDeliveries
DELETE /api/account  {password}                   -> 400 ("confirm"/"DELETE" required)
DELETE /api/account  {password: wrong, confirm}   -> 403, session still valid afterwards
DELETE /api/account  {password, confirm:"DELETE"} -> 200 {ok:true, deletedWorkspace:true}
   then: /api/workspace -> 401, workspaces row gone, records cascaded, users row gone
owner with a teammate still present               -> 409 "other members", both accounts intact
non-owner member deleting their own account       -> 200 {deletedWorkspace:false}, workspace intact
```
